# Phase 1 Erlang Abstract Format Subset

## Production boundary

Phase 1 lowers its fixed A-Lang semantic fixture directly to Erlang Abstract
Format and invokes `compile:forms/2` from the pinned OTP release. It does not
generate Erlang source, Core Erlang, BEAM assembly, or a `.beam` file by hand.

The supported top-level module shape is exactly:

```text
-module(phase1_counter_v1).
-export([start/1]).
start(Parent) -> ...
```

The text above explains the shape; it is not compiler input. The implementation
constructs Abstract Format terms directly from the typed fixture introduced in
Section 1.3.

## Allowed forms

The build-only subset validator accepts:

- fixed `module` and `export` attributes;
- one `start/1` function with bounded clauses;
- variables from the compiler's fixed variable-name set;
- fixed atoms, bounded integers, strings used only inside binary segments,
  binaries, tuples, lists, and clauses;
- `case` and `receive` control flow;
- match expressions;
- unary and binary operators from the closed operator set;
- calls to explicitly allowlisted `erlang` BIFs; and
- stable integer source annotations generated by the lowering pass.

The Phase 1 runtime-call allowlist is:

```text
erlang:byte_size/1
erlang:exit/1
erlang:external_size/1
erlang:is_binary/1
erlang:is_integer/1
erlang:is_pid/1
erlang:node/0
erlang:node/1
erlang:self/0
```

The inspected BEAM import allowlist additionally admits
`erlang:'+'/2`, `erlang:get_module_info/1`, and
`erlang:get_module_info/2`. The addition operation implements the fixed
counter transition, while the OTP compiler adds the module-information calls
for ordinary modules. An allowlisted call need not appear as an import when
OTP recognizes it as a BIF or lowers it directly.

## Forbidden forms

The validator rejects every form not explicitly accepted, including:

- dynamic or local calls;
- remote calls outside the fixed `erlang` allowlist;
- `fun`, try/catch, comprehensions, maps, records, and dynamic apply;
- NIF, port, filesystem, network, code-loader, and process-spawn calls;
- arbitrary attributes, exports, modules, functions, and atoms;
- non-integer or unstable source annotations;
- excessive form depth, clause count, tuple width, or list length; and
- any attempt to encode a runtime operation name from input data.

## Validation and compilation order

The compiler boundary must execute these steps in order:

1. read and validate `toolchain.config`;
2. compare the exact OTP, ERTS, and architecture values with the running VM;
3. validate the closed A-Lang Abstract Format subset;
4. call `compile:forms/2` with `strong_validation` and no code generation;
5. reject all errors and warnings;
6. compile again with `binary`, `deterministic`, `no_debug_info`, and
   `no_docs`;
7. reject all emission errors and warnings;
8. inspect module, exports, imports, attributes, and compile information with
   `beam_lib`;
9. reject a wrong module, unexpected export, or forbidden import; and
10. return the binary to the Section 1.3 packager without loading it.

Only the Section 1.4 harness may call the BEAM loader, and only after manifest
verification.

## Failure contract

Subset, OTP validation, emission, and inspection failures return tagged error
terms. The build command prints the expected and actual toolchain values for a
version mismatch and exits nonzero. No failed form set produces an accepted or
loaded artifact.
